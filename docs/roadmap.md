# DigestDesk 下一阶段 Roadmap

本文档记录多用户架构完成后的下一阶段推进顺序。

相关文档：

- [多用户架构](/Volumes/Sheng/AIcases/digestdesk/docs/MULTI_TENANT_ARCHITECTURE.md)

## 1. 当前阶段目标

当前已经完成的重点是：

- 多用户核心业务规则统一
- 全局内容资产与用户私有关系分层完成
- Clerk 登录链路接入
- 文档资产拆分完成

当前阶段不再继续扩展大功能，先把这套基线站稳。

## 2. 第一阶段：部署与验证

目标：

- 将当前版本部署到云平台
- 观察真实运行结果
- 收集首轮联调反馈

重点关注：

- Google 登录是否正常
- `/api/auth/me` 是否正常建档
- 多账号订阅与日报是否隔离
- 同一 feed 是否能被多个用户复用订阅
- 取消订阅与重新订阅是否符合规则
- 日报是否按用户时区 `T-1` 生成

说明：

- 当前阶段先以真实结果为准
- 不预先做过多性能优化

## 3. 第二阶段：补最小运维资产

目标：

- 让部署、维护和后续接手变得清晰可重复

建议补齐：

- 环境变量说明
- Clerk 开发/生产配置说明
- 数据库表职责说明
- 部署后首轮检查清单

这一阶段的产出重点不是功能，而是可维护性。

## 4. 第三阶段：商业化边界准备

目标：

- 为后续收费模式做边界准备

优先事项：

- 订阅数上限设计
- 用户计划等级预留
- quota / plan 的接口位和数据结构预留
- 关键用户行为的可审计性

建议方向：

- 先采用统一月费模型
- 配合订阅源数量上限

## 5. 第四阶段：能力层增强

目标：

- 在结构稳定后，继续增强产品能力

方向包括：

- 更好的订阅导入能力
- 更好的日报编辑与展示能力
- YouTube 相关能力增强
- AI 总结能力继续深化

说明：

- AI 能力放在这一步，而不是当前优先项
- 先确保多用户、规则、时区、隔离和生命周期稳定

## 6. 后续性能优化项

当前可接受但后续值得优化的方向：

- 日报生成的预生成机制
- 调度器的用户扫描优化
- 更成熟的任务队列
- 更细粒度的监控与耗时统计

这些不阻塞当前阶段，但适合在真实运行后再决定优先级。

## 7. 总结

下一阶段整体顺序是：

1. 先部署并观察测试结果
2. 再补最小运维资产
3. 再做商业化边界准备
4. 最后再继续扩展能力层与 AI 功能
