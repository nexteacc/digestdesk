# DigestDesk — Master Plan

> 你的个人编辑助手：自动阅读你订阅的 Substack，每天/每周为你编辑一份专属 Digest。

---

## 1. 为什么做

### 问题

知识工作者订阅了大量 Substack Newsletter，但：

- 每天 5-15 封邮件涌入，没时间逐篇阅读
- 怕错过重要内容，但精力有限
- 邮箱被淹没，阅读体验碎片化
- 信息焦虑：该看的太多，能看的太少

### 现有方案的不足

| 方案 | 问题 |
|------|------|
| 在邮箱里逐封看 | 效率低，重要和不重要混在一起 |
| Feedly 等 RSS 阅读器 | 聚合了但不总结，还是要自己读 |
| Readwise Reader | 深度阅读工具，定位是"读得更好"而非"省时间" |
| AI 邮件插件 | 单篇总结，缺少跨源聚合的全局视角 |

**没有人在帮用户"编辑"信息，只有人在帮用户"搬运"信息。**

---

## 2. 为谁做

### 目标用户

**订阅了 3 个以上 Substack 的知识工作者**

具体画像：
- 产品经理、创业者、投资人、技术从业者、内容创作者
- 订阅 Substack 是为了保持行业敏感度
- 英文阅读能力良好，但时间成本高
- 每天有固定的"信息消费时段"（早晨、午休、通勤）
- 愿意为节省时间付费

### 非目标用户

- 只订阅了 1-2 个 Newsletter 的轻度用户（痛点不强）
- 追求深度精读的学术型用户（需要原文）
- 不使用 Substack 的用户（当前阶段）

---

## 3. 做什么

### 产品定义

**DigestDesk 是个人编辑助手。**

它像一位私人编辑：
1. **订阅** — 用户告诉编辑"我关注哪些作者"
2. **阅读** — 编辑帮你读完所有更新
3. **编辑** — 提炼每篇的核心观点和关键洞察
4. **交付** — 按时把一份精华 Digest 推送给你

### 核心交付物

- **日报**：每日推送，5 分钟读完昨日所有更新

### MVP 范围（当前阶段）

| 包含 | 不包含 |
|------|--------|
| Substack 订阅管理 | YouTube 频道（Phase 2） |
| RSS 抓取 + AI 摘要 | Podcast / Twitter / Reddit |
| 日报生成 | 用户间社交分享 |
| 网页阅读（手动打开） | 浏览器推送通知（MVP 后） |
| Substack 公开信息获取 | 邮件投递 |
|  | 付费墙内容 |

## 4. 差异化定位

### 一句话

> **别人做阅读器，我们做编辑助手。**

### 与竞品的根本区别

| 维度 | 阅读器类产品 | DigestDesk |
|------|------------|------------|
| 用户行为 | 主动去"读" | 被动接收"报纸" |
| 信息处理 | 搬运原文 | AI 编辑提炼 |
| 交付形式 | 信息流/列表 | 有节奏的日报 |
| 使用频率 | 随时刷 | 到点看，看完走 |
| 核心价值 | 聚合 | 压缩 |

### 产品节奏感

DigestDesk 不是一个你"随时打开"的工具，而是一份有节奏的出版物：
- 日报：每天早上 8 点推送
- 没有新内容时不推送（不打扰）

这种节奏感创造仪式和习惯，是留存的基础。

---

## 5. 产品远景

当前 MVP 聚焦 Substack，但 DigestDesk 的远景是**个人信息中枢**：

```
Phase 1（当前）：Substack Newsletter → 日报
Phase 2（下一步）：+ YouTube 频道更新与总结
Phase 3（未来）：+ 更多信息源（Podcast、RSS 通用源等）
```

最终形态：**一个人的编辑部，所有你关注的深度内容，汇聚成一份只属于你的报纸。**

## 6. 成功指标

### MVP 阶段指标（当前可度量）

| 指标 | 目标 | 含义 |
|------|------|------|
| 日报生成成功率 | >95% | 手动触发生成日报，不报错不超时 |
| 单篇摘要延迟 | <10 秒 | 从发起到 AI 返回结构化摘要 |
| 日报生成延迟 | <60 秒 | 10 篇文章的完整日报生成时间 |
| RSS 同步成功率 | >90% | 定时同步不丢 Feed、不重复 |
| 内容抓取覆盖率 | >80% | Jina Reader + Turndown 成功获取全文的比例 |
| Zod 解析成功率 | >99% | AI 输出通过 schema 验证的比例 |

### 产品成熟期指标（需埋点/账户体系后度量）

| 指标 | 目标 | 含义 |
|------|------|------|
| 首份 Digest 生成率 | >80% | 注册后成功看到第一份 Digest 的比例 |
| 日报打开率 | >60% | 推送后实际打开阅读 |
| 7 日留存 | >40% | 一周后仍在使用 |
| 平均阅读时长 | 3-5 分钟 | 太短=内容不够，太长=不够精炼 |
| 原文点击率 | 20-30% | 摘要引发兴趣但不完全替代 |
| 摘要满意度 | >4/5 | 用户对 AI 摘要质量的主观评分 |

## 7. 关键风险

| 风险 | 影响 | 应对 |
|------|------|------|
| AI 摘要质量不达标 | 用户失去信任，产品无价值 | 先用最强模型，早期收集用户反馈迭代 prompt |
| 使用频率衰减 | DAU 下降，产品变成"注册后不用" | 浏览器推送建立习惯，周报做召回 |
| Substack 限制 API 访问 | 数据源断裂 | RSS 为主（官方支持），API 为辅；搜索 API 通过 CF Worker 代理绕过 IP 封锁 |
| 冷启动门槛高 | 用户注册后不知道订阅什么 | 提供热门 Substack 推荐列表 |
| 信息同质化 | 用户感知不到差异 | 个性化编排，突出用户独特的订阅组合 |

## 8. 技术基础

### 当前技术栈

**前端（已建成）：**
- React 19 + TypeScript + Vite
- Tailwind CSS + shadcn/ui 组件库
- wouter 路由（hash-based）
- API 客户端层（src/lib/api.ts）— 统一封装后端 API 调用

**后端（MVP 已建成）：**
- Express.js v5（端口 8080）
- SQLite + Drizzle ORM（better-sqlite3，WAL 模式）
- Vercel AI SDK（ai + @ai-sdk/google + @ai-sdk/openai）— 多模型支持
- 默认 Gemini 2.5 Flash（Google API Key 优先，1M 上下文窗口，不截断全文）；可切换 gpt-5-nano（OpenAI 备选）
- Jina Reader API + Turndown（内容抓取）
- node-cron（每天 8:00 RSS 同步）+ rss-parser
- p-limit（5 篇并发摘要生成）
- dotenv（环境变量管理）

### Substack 数据获取能力

| 方式 | 可靠性 | 数据范围 |
|------|--------|----------|
| RSS Feed (`/feed`) | 高（官方支持） | 文章标题、全文HTML、作者名、发布日期 |
| 搜索 API (`/api/v1/publication/search`) | 中（非官方，生产环境需 CF Worker 代理） | 出版物名称、Logo、简介、URL |
| 非官方 API (`/api/v1/archive`) | 中（可能变动） | 文章列表、封面图、互动数据 |
| 非官方 API (`/api/v1/posts/{slug}`) | 中 | 单篇完整内容、评论数、反应数 |
| Publication 元信息 | 高 | 出版物名称、描述、Logo |

### 需要补充的能力（MVP 后）

- 用户账户体系
- 浏览器推送（Web Push API）
